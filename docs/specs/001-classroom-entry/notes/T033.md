# T033 구현 노트: E2E (학생 입장 전체와 기기 묶음)

> 스펙과 plan에 없는, 구현하면서 내가 세운 계획과 판단의 요지다. 스펙이 우선한다. 고칠 부분이 있으면 알려 달라.

## 스펙과 plan에서 읽은 것

- tasks: Playwright 브라우저 컨텍스트 두 개로 확인한다. A에서 요청한 코드를 B에서 입력하면 일반 오류이고 A에서는 통과한다. 입장 끝까지 간다. 로그인 유지 켬/끔으로 브라우저를 닫았다 다시 연다. 메일은 `OutboxMailer`로 확인한다.
- plan: E2E는 Playwright(1.65.1, 의존성 표에서 확인됨)로 한다. 학생 입장 전체(AC24~AC28), 기기 묶음(AC33), 390px 가로 스크롤 없음을 본다.

## 의존성 (C17, 2026-11-22 다시 조회)

- `@playwright/test` 1.65.1: plan 표와 같은 버전이다. 2026-11-13 공개, 최근 한 달 약 5.2억 다운로드. 하위 의존성은 `playwright-core`(같은 버전) 하나다. `--save-exact`로 고정했고 lockfile을 커밋한다.
- 테스트용 Chromium v1255(Playwright 1.65.1이 쓰는 빌드)가 이 Mac에 없었다. 사용자 승인을 받아 Playwright 공식 CDN에서 받았다(약 293MB, `~/Library/Caches/ms-playwright`). 저장소에는 들어가지 않는다.

## 내가 정한 것 (스펙 밖)

1. **E2E 전용 서버 `client/e2e/server.py`**: 운영과 같은 구성(빌드한 클라이언트를 FastAPI가 같은 출처에서 내려줌)이다. 교수 로그인은 가짜 GitHub(누르면 바로 로그인)이고, 메일은 메모리(`OutboxMailer`)에 모은다. **테스트만 쓰는 경로 `GET /api/test/last-code?to=`**가 그 주소로 보낸 마지막 코드를 알려 준다. 이 경로는 이 스크립트 안에만 있고 운영 앱(`create_app`)에는 없다. 실행할 때마다 새 임시 DB로 시작한다.
2. **교수 쪽 준비는 API로 한다**(강좌 만들기, 명단, 승인, 대기 중인 인증 조회). 이 E2E는 학생 입장을 보는 것이고, 교수 화면의 키보드 확인은 T034가 한다.
3. **"브라우저를 닫았다 다시 연다"는 새 컨텍스트로 흉내 낸다.** 만료 시각이 없는 쿠키(브라우저를 닫으면 사라지는 쿠키)는 버리고, 만료 시각이 있는 쿠키(기기 쿠키, 로그인 유지를 켠 로그인 쿠키)만 가져간다. 실제 브라우저가 닫힐 때와 같다. AC35(켬 → 바로 입장)와 AC36(끔 → 이메일부터)이 서로를 확인한다. 흉내가 세션 쿠키를 버리지 못하면 AC36이 실패한다.
4. **테스트마다 이메일이 다른 학생을 만든다.** 서버와 메일함을 모든 테스트가 같이 쓰기 때문이다. 처음에는 같은 이메일을 써서 이전 테스트의 코드를 읽는 바람에 5개가 실패했다(테스트 쪽 문제).
5. **AC33 확인 방법**: B는 같은 이메일을 넣으면 60초 안이라 코드를 새로 받지 않고 코드 단계로 온다(T027의 동작). 여기서 A의 코드를 넣으면 "코드가 맞지 않습니다."만 보인다(남은 횟수 없음). 그 뒤 A에서 한 번 틀리면 "4번 더"가 보인다. 즉 B의 시도는 A의 횟수를 쓰지 않았다. A는 원래 코드로 통과한다.
6. **AC32(다시 받기)는 실제로 60초를 기다린다.** 서버 시계를 바꿀 수 없는 실제 프로세스라서 그렇다. 이 테스트 하나가 1분쯤 걸린다(`test.slow()`).
7. 그 밖에 넣은 것: 입장 요청 → 승인 → 같은 이메일로 입장(AC38~AC41), 교수님께 알리기 → 교수가 알려 준 코드로 입장 → "사용됨"(AC44~AC47), 같은 기기로 다른 강좌(AC37, 새 닉네임), 이메일·코드 단계의 390px 가로 스크롤 없음(AC51).
8. **CI에 `e2e` 작업을 더했다.** Python 서버 설치 → `npm ci` → Chromium 설치 → `npm run test:e2e` 순서다. 필수 체크로 둘지는 브랜치 보호 규칙의 일이라 사용자가 정한다.

## 확인한 것

- E2E 9개가 두 번 연속 모두 통과했다(각 1.2분). 클라이언트 단위 테스트 382개와 `svelte-check`도 그대로 통과한다(vitest는 `src/`만 보므로 E2E 파일과 섞이지 않는다). 서버는 바뀌지 않았다.

## 일부러 하지 않는 것

- AC36에서 다시 인증한 뒤 닉네임이 같은지는 여기서 보지 않았다. 다시 인증하려면 60초를 한 번 더 기다려야 하고, 같은 닉네임은 서버 테스트(T020, T024)와 T028 실제 화면 확인에서 이미 봤다.
- 키보드만으로 로그인부터 입장까지 가는 것과 포커스 링·44px 점검은 T034다. 여기서는 이메일 제출에 Enter를 쓰는 정도만 했다.
- 다른 브라우저(WebKit, Firefox)와 실기기는 이번 범위가 아니다. 실기기는 T036에서 본다.

## lockfile (CI에서 찾아 고친 것)

- 처음 올린 lockfile로 CI의 `npm ci`가 실패했다("`@emnapi/core`, `@emnapi/runtime`이 lockfile에 없다"). 로컬 npm은 11(Node 24), CI는 Node 22에 딸린 npm 10이다. npm 11로 설치하면서 npm 10이 요구하는 선택 의존성 두 항목이 lockfile에서 빠졌다.
- main의 lockfile에서 다시 시작해 **npm 10(10.9.4)으로** Playwright만 더했다. 이제 lockfile은 Playwright 항목만 늘었고, npm 10과 npm 11 모두 `npm ci`가 된다. 앞으로 클라이언트 의존성을 바꿀 때도 CI와 같은 npm 10으로 lockfile을 만든다.

## 결정된 질문

- CI의 `e2e` 작업을 필수 체크로 둔다(사용자, 2026-11-22). 브랜치 보호 규칙에 넣는 것은 사용자가 한다.
