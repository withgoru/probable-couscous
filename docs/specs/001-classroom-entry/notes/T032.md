# T032 구현 노트: 서버 재시작 복원 통합 테스트

> 스펙과 plan에 없는, 구현하면서 내가 세운 계획과 판단의 요지다. 스펙이 우선한다. 고칠 부분이 있으면 알려 달라.

## 스펙에서 읽은 것

- 오류와 예외 동작: 서버를 다시 시작해도 로그인 유지 중인 학생, 교수 로그인, 명단, 닉네임, 입장 요청, 대기 중인 인증이 그대로 남는다(C13).
- tasks: 명단, 챌린지, 로그인 유지, 입장 요청, 대기 중인 인증이 서버 프로세스를 다시 만든 뒤에도 남는다.

## 내가 정한 것 (스펙 밖)

1. **먼저 메모리에만 있는 상태를 찾았다.** 모듈 전역에 있는 값은 모두 상수였다. 실행 중 상태(실시간 버스, 메일 작업의 초당 상한 창)는 앱 객체에만 있다. 교수 로그인 확인 값(OAuth state)은 쿠키에 있다. 그래서 고칠 코드는 없었고 테스트만 더했다.
2. **두 가지 방식으로 확인한다.**
   - `test_restart.py`: 같은 DB로 앱을 새로 만든다(정상 종료 → 새 앱, 새 메일함, 새 실시간 버스). 빠르고 항목별로 나눠 볼 수 있다.
   - `test_restart_process.py`: 실제 uvicorn 프로세스를 띄워 요청을 처리하게 한 뒤 **SIGKILL로 종료 처리 없이 죽이고**, 같은 DB로 새 프로세스를 띄운다. "답을 받은 쓰기는 남는다"를 실제 프로세스로 확인한다. 이 테스트는 1초쯤 걸린다.
3. **브라우저 쪽은 쿠키를 그대로 가져간다.** 서버가 다시 떠도 학생과 교수의 브라우저는 쿠키를 갖고 있기 때문이다.
4. **확인하는 것**:
   - 교수 로그인이 남고, 로그아웃도 여전히 된다. 재시작 전에 시작한 GitHub 로그인을 재시작 뒤에 마칠 수 있다.
   - 명단과 입장 여부가 남는다.
   - 로그인 유지: 이메일 없이 바로 입장하고 닉네임이 같다.
   - 재시작 전에 받은 코드로 입장할 수 있다. 틀린 횟수와 다시 받기 60초 간격도 이어진다.
   - 입장 요청이 남는다.
   - 대기 중인 인증: 같은 코드가 보이고 그 코드로 입장할 수 있다.
   - 보내기 전에 서버가 다시 떠도 새 서버가 코드 메일을 보낸다.
   - 끊긴 로그인과 보관은 그대로다.
   - 다시 시작해도 마이그레이션이 두 번 적용되지 않는다.
5. **테스트가 실제로 실패할 수 있는지 확인했다.** 두 번째 서버를 다른(빈) DB로 띄우게 바꾸면 8개 중 7개가 실패했다. 남은 1개는 "재시작 전에 시작한 로그인을 마침"인데, 확인 값이 쿠키에 있어 DB와 무관하므로 맞게 통과한 것이다.
6. 한 번에 모두 보는 테스트와 프로세스 강제 종료 테스트 둘에 constitution 표시를 했다(C13 필수 회귀).

## 한계

- SIGKILL로는 운영체제의 디스크 캐시가 남아 있으므로, 전원이 꺼질 때의 내구성(`synchronous=FULL`이 지키는 부분)까지는 확인하지 못한다. 이 테스트가 보장하는 것은 "서버가 성공으로 답한 쓰기를 메모리에만 들고 있지 않다"이다.
- 실시간 연결(WebSocket)은 재시작하면 끊기고, 화면이 다시 연결해 목록을 새로 받는다. 이 부분은 T029에서 실제 화면으로 확인했다.
