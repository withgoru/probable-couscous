# T009 구현 노트: 수업 WebSocket(넘기기·확인·현황)

> 스펙과 plan에 없는, 구현하면서 내가 세운 계획과 판단의 요지다. 스펙이 우선한다. 고칠 부분이 있으면 알려 달라.

## 스펙과 plan에서 읽은 것

- AC13·AC17·AC20·AC25: 교수가 넘기면 다른 교수 화면, 프로젝터, 학생이 같은 위치를 받는다. 프로젝터는 넘길 수 없다.
- AC15·C7: "따라가는 중 N명 · 직접 넘겨 보는 중 M명", 누가 어느 쪽인지는 보이지 않는다.
- plan: `/ws/class/{강좌}`, 연결 때 `class.view`, 프로젝터는 교수 연결에 `role=projector`. 교수 `goto{회차, 슬라이드, 단계, req}` → 범위 검사 → DB → `ack{req, version}` → `position` 발행. 학생 `mode{follow|browse}` → 교수에게만 `presence`. 현황은 DB에 쓰지 않는다.

## 내가 정한 것 (스펙 밖)

1. **연결 순서는 001 관리 화면 WebSocket과 같다.** 권한 판단(`guard_class`)과 `Origin` 검사를 연결 전에 하고, 구독을 건 뒤 `ready{role}`을 보낸다. 화면은 `ready` 뒤 `GET …/live`(T008)로 상태를 받는다. `guard_class`가 WebSocket에도 걸리도록 받는 인자를 `HTTPConnection`으로 바꿨다(동작은 같다).
2. **연결마다 구독은 하나.** 현황(`presence`)도 같은 방에 "교수만" 표시를 붙여 발행하고, 프로젝터·학생 연결은 걸러 낸다. 방을 둘로 나누면 두 큐 사이의 순서가 보장되지 않아서 이렇게 했다. 표시는 화면에 보내기 전에 뗀다.
3. **넘기기 범위**
   - 슬라이드는 1부터 묶음의 슬라이드 수까지다. 묶음이 없으면 1번뿐이다.
   - 서버는 슬라이드마다 단계 수를 모른다(애드온이 화면에만 알린다). 그래서 단계는 0~999의 정수만 받는다. 실제 단계 범위는 교수 화면과 애드온이 지킨다.
   - 숫자처럼 보이는 글자, 소수, `true`도 거절한다.
   - 진행 중이 아닌 회차, 다른 강좌의 회차, 없는 회차는 모두 `not_live`다.
4. **같은 위치로 넘기면** DB를 쓰지 않고 지금 `version`으로 `ack`만 한다. 발행도 하지 않는다.
5. **거절은 연결을 닫지 않는다.** `error{req, reason, message}`로 답한다. reason은 `bad_message`, `not_allowed`(학생·프로젝터의 `goto`), `not_live`, `out_of_range`이고, message는 화면에 보일 한국어다. `req`는 64자 이하 글자나 정수일 때만 돌려준다.
6. **현황 세기**
   - 학생 한 명(멤버십)은 한 번만 센다. 화면이 여러 개면 하나라도 따라가는 중이면 따라가는 중이다.
   - 학생 연결은 처음에 따라가는 중으로 센다(AC25).
   - 새 교수 화면은 `ready` 바로 뒤에 지금 현황을 받는다.
   - 현황은 `app.state.presence`(메모리)에 두고 연결이 끊기면 뺀다.
7. **보내기는 연결마다 하나씩.** 구독 전달과 `ack`·`error`가 같은 연결에 동시에 쓰지 않도록 잠금을 둔다.
8. **DB 작업은 스레드에서 한다.** 넘기기는 `run_in_threadpool`로 이벤트 루프를 막지 않는다. 연결 하나는 받은 메시지를 차례로 처리한다.
