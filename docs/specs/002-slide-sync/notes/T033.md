# T033 구현 노트: 서버 — 비공개 묶음 파일 막기

> 스펙과 plan에 없는, 구현하면서 내가 세운 계획과 판단의 요지다. 스펙이 우선한다. 고칠 부분이 있으면 알려 달라.

## 스펙과 plan에서 읽은 것

- AC50: 비공개 묶음의 슬라이드는 수업 중 따라가기 밖에서는 학생에게 내주지 않는다. 학생이 주소를 직접 열어도 볼 수 없다. 비공개로 바꾸면 그때부터 내주지 않는다.
- plan: 판단은 서버의 `/decks/…` 권한 한 곳에서 한다(C8). 교수와 프로젝터는 늘 받는다.

## 내가 정한 것 (스펙 밖)

1. **학생이 받는 조건**: 공개 묶음이거나, 그 묶음의 회차가 진행 중일 때다. 지운(바꾸기로 밀려난) 묶음은 원래부터 받지 못한다.
   - 진행 중인 다른 회차가 있어도, 그 회차의 묶음이 아니면 받지 못한다.
   - 이어서 하기로 다시 진행 중이 되면 다시 받는다.
2. **늘 받는 쪽**: 교수만 늘 받는다(프로젝터는 교수 로그인이다). 학생만 막는 대신 "교수가 아니면 막는다"로 썼다. 나중에 다른 종류의 사용자가 생겨도 비공개 묶음이 새지 않게 하려는 것이다(리뷰에서 찾음).
3. **막을 때의 응답**
   - 없거나 지운 묶음과 똑같은 404("찾을 수 없습니다.")다. 어떤 묶음이 있는지 알리지 않는다.
   - 파일이 없는 비공개 묶음도 학생에게는 410이 아니라 이 404다. 410이면 묶음이 있다는 것을 알린다(변형 검사에서 찾음).
   - 응답은 저장하지 않는다(`no-store`). 이어서 하거나 공개한 뒤에 막힌 응답이 남지 않게 한다.
4. **학생 캐시**
   - 교수에게는 지금처럼 해시가 붙은 파일을 1년 캐시한다.
   - 학생에게는 모든 파일을 매번 확인한다(`private, no-cache`, 확인은 304로 끝난다). 수업 중에 받은 비공개 묶음 파일이 1년 캐시에 남아 수업 뒤 주소로 바로 열리는 것을 막는다(리뷰에서 찾음).
   - 학생 200명이 수업 시작에 받는 양은 그대로다. 다시 열 때 파일마다 확인 요청이 한 번씩 늘어난다(T030 측정에서 함께 본다).
   - 수업 중에 학생이 직접 저장한 파일은 막지 못한다(spec 미결정 질문, plan 위험 5).
5. **다시 보기의 임시 처리**
   - 비공개 묶음의 다시 보기는 이제 파일을 받지 못해, 그대로 두면 슬라이드 자리에 오류 글이 보인다.
   - 그래서 iframe 대신 "이 회차의 슬라이드는 공개되지 않았습니다."를 보이고 넘기기 버튼을 감췄다(AC39 문구). 자료는 그대로 보인다.
   - 다시 보기의 나머지 정리(`limit` 없애기, 넘기기 규칙)는 T037이 한다.

## 확인한 것

- 테스트를 먼저 썼다(구현 전 6개 실패 확인).
  - `test_private_deck_files.py` 15개: 공개 묶음은 어느 상태에서나, 비공개는 진행 중에만(예정·종료는 막힘, 이어서 하기는 받음), 비공개로 바꾸면 바로, 다른 회차의 묶음, 바꾼 묶음, 교수와 프로젝터, 없는 묶음과 같은 응답, 파일 없는 묶음, 캐시
  - 다시 보기 1개(비공개 묶음이면 공개되지 않았다는 안내와 자료만)
  - 기존 학생 파일 테스트는 묶음을 공개한 뒤 받도록 고쳤다.
- 검증은 서브에이전트가 했다.
  - 변형 검사: 15개 중 10개를 잡았다. 진짜 빈틈 1개(파일 없는 비공개 묶음에 410)는 테스트를 더해 잡았다. 나머지 4개는 DB 규칙(외래 키, 지운 묶음은 앞에서 막힘) 때문에 결과가 같았다.
  - 코드 리뷰: 우회 경로는 없었다. 찾은 것과 처리는 이렇다.
    - 학생 캐시에 1년 남음: 매번 확인하게 했다.
    - 다시 보기에 오류 글: 안내로 바꿨다.
    - 학생만 막음: 교수가 아니면 막게 했다.
    - 거절 응답 저장: `no-store`를 붙였다.
    - 순서 테스트 없음: 테스트를 더했다.
  - 고친 것은 변형 4개로 다시 확인했다. 3개를 잡았다. 남은 하나(교수가 아니면 막음 ↔ 학생만 막음)는 지금 사용자 종류(익명, 교수, 학생)로는 결과가 같다. 익명은 그 앞의 권한 판단에서 막히기 때문이다.
