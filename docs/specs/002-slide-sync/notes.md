# 002-slide-sync 메모

## 미결정

- **200개 브라우저 판정 미확정.** 프로토타입 검증 1번에서 서버 중계는 200개 p95 2.9ms로 통과했지만, 브라우저는 Chrome 한 대에 페이지 200개를 띄운 단일 기기 측정(p95 989ms, max 1679ms)이라 CPU 경쟁이 섞였다. 큰 강의에서 쓰기 전에 실기기 여러 대로 확정한다. (`docs/specs/000-prototype-validation/README.md` 1번)

## 위험 1·4. 200명 동기화와 첫 로딩 측정 (T030)

### 방법

- 스크립트: `server/scripts/load_class.py`(001 `load_codes.py`와 같은 방식). 실행은 `server/`에서 `python scripts/load_class.py --students 200 --moves 10 [--deck 묶음.zip] [--json]`.
- 순서
  1. 실제 서버 프로세스(E2E 전용 서버: uvicorn 한 프로세스, SQLite `synchronous=FULL`)를 띄운다.
  2. 묶음(기본은 테스트용 4장)으로 수업을 시작한다.
  3. 학생 N명이 각자 다른 기기(쿠키)로 이메일·코드 입장을 거쳐 수업 WebSocket에 붙는다.
- 재는 것
  - **첫 로딩**: 모든 학생이 같은 순간에 묶음의 첫 화면 파일을 받는 시간이다. index.html과 그것이 바로 부르는 JS·CSS 7개, 모두 8개 523KB다. 학생마다 휴대폰 브라우저처럼 연결을 6개까지 열고, 입장 때와 다른 새 연결로 받는다.
  - **동기화**: 교수 연결이 `goto`를 보낸 순간부터 각 학생 연결에 그 `position`이 닿기까지의 시간이다. 교수가 0.3초 간격으로 10번 넘긴다.
    - 서버의 DB 기록(fsync)과 측정 쪽 한 이벤트 루프가 200개 연결을 처리하는 시간이 들어 있어, 서버 몫의 위쪽 끝이다.
    - 마지막 넘기기 뒤 1초 안에 닿지 않으면 유실로 센다.
  - **유실**: 위치를 받지 못한 횟수의 합, 그리고 마지막 위치가 DB에 남지 않았으면 1(C13).
  - **첫 로딩 실패**: 묶음을 받지 못한 학생 수. 유실이나 첫 로딩 실패가 있으면 종료 코드가 1이다.
- 한계
  - 프로토콜 수준이다. 브라우저가 iframe에 그리는 시간은 들어가지 않는다.
  - 측정 컴퓨터 한 대가 서버이자 학생 200명이다.
  - **첫 로딩은 실제보다 작다**: 테스트용 묶음이고, 나중에 불러오는 조각(예: 70KB)과 그림(예: 94KB)은 들어가지 않는다. plan 위험 4가 말한 "보통 크기 묶음(그림 10장 안팎)"은 `--deck`으로 실제 묶음을 올려 다시 잰다.
  - **plan 위험 1(a)의 "노트북 여러 대 × 헤드리스 브라우저" 측정은 하지 않았다**(컴퓨터 한 대). 아래 "다시 잴 것"에 방법을 적었다.

### 결과 (2026-11-27, MacBook 한 대, 서버와 측정이 같은 컴퓨터, 학생 200명)

| 실행 | 동기화 p50 / p95 / 최대 | 유실 | 첫 로딩 p50 / p95 / 최대 | 첫 로딩 실패 |
|---|---|---|---|---|
| 1 | 5.8 / 10.0 / 11.8ms | 0 / 2000 | 3.22 / 3.23 / 3.24초 | 0 |
| 2 | 7.7 / 11.5 / 12.7ms | 0 / 2000 | 2.94 / 2.95 / 2.96초 | 0 |
| 3 | 8.0 / 11.7 / 13.4ms | 0 / 2000 | 2.89 / 2.91 / 2.91초 | 0 |
| 4 | 7.5 / 11.0 / 12.2ms | 0 / 2000 | 2.93 / 2.95 / 2.95초 | 1명(ConnectError) |

- **동기화(위험 1)**
  - 서버가 200명에게 위치를 나눠 주는 데는 p95 12ms 안쪽이고 유실이 없다. 마지막 위치는 늘 DB에 남았다.
  - AC25의 1초 가운데 서버 몫은 작다. 남은 몫은 휴대폰 망과 브라우저가 그리는 시간이며, 여러 컴퓨터와 실기기로 다시 잰다.
- **첫 로딩(위험 4)**
  - 200명이 같은 순간에 523KB를 받으면 모두 받는 데 약 3초다. 서버 한 프로세스가 약 100MB를 내보낸다.
  - 처음에는 입장 때 열어 둔 연결로 받았는데, 4번 중 3번은 2~27명이 실패했다(대부분 `ReadError`). 입장이 끝나기까지 약 25초가 걸리는데, 그사이 서버가 쉬던 연결을 닫았다(uvicorn 기본 keep-alive 5초). 측정 방식의 문제였다. 새 연결로 받게 고친 뒤에는 4번 중 한 번 1명만 실패했다(`ConnectError`).
  - 남은 `ConnectError`는 연결 대기열이 넘쳤을 가능성이 크다. 측정 컴퓨터(macOS)의 대기열 상한은 128개(`kern.ipc.somaxconn`)이고, 학생 200명 × 연결 6개가 한꺼번에 몰린다. 상한을 바꿔 확인하려면 관리자 권한이 필요해 확인하지 못했다.
  - 실제 수업에서는 휴대폰마다 시작 시각이 조금씩 다르다. 배포 서버(Linux, 기본 4096)와 리버스 프록시(HTTP/2면 휴대폰당 연결 1개)도 다르다.
  - 그래도 묶음을 받지 못한 학생은 지금 화면에서 15초 뒤 "슬라이드를 열 수 없습니다"를 보고 스스로 다시 받지 못한다.
- 학생 10명으로 돌리는 테스트(`tests/test_load_class_script.py`)가 확인하는 것: 스크립트가 숫자를 내는지, 유실이 있으면 실패하는지.

### 결정 (사용자, 2026-11-27)

- T030은 여기서 끝낸다. 여러 컴퓨터·헤드리스 브라우저 측정(plan 위험 1(a))은 실기기 측정과 함께 배포 뒤에 한다.
- 첫 로딩 실패 대응은 아래 후보 2(공개 묶음은 학생도 해시 파일을 오래 캐시하고, 입장할 때 미리 받기)로 한다. 이 일은 새 작업으로 tasks에 더한다.

### 대응 후보

1. **슬라이드를 열지 못하면 다시 받기**: 학생 화면이 "열 수 없습니다" 전에 iframe을 다시 띄운다. 여러 학생이 같은 순간에 다시 받지 않게 몇 초 안에서 흩어지게 한다. 클라이언트만 바꾸면 된다.
2. **학생도 해시 파일을 오래 캐시하기 + 입장할 때 미리 받기**: 지금은 학생이 모든 묶음 파일을 매번 확인한다(T033, 수업 뒤 캐시로 비공개 묶음을 여는 것을 막으려고).
   - 그래서 대기 화면에서 미리 받아 두어도, 수업 시작에 파일마다 확인 요청이 다시 몰린다.
   - 공개 묶음만 해시 파일을 오래 캐시하면, 미리 받기가 몰림을 실제로 줄인다. 비공개 묶음 파일은 수업 밖에서 내주지 않아(AC50) 미리 받을 수 없다.
3. **배포 설정**: 리버스 프록시(HTTP/2), 대기열(backlog)을 늘린 uvicorn, 묶음 파일을 프록시가 직접 내주기. 배포 대상이 정해질 때 함께 정한다.

### 다시 잴 것

- **여러 컴퓨터·헤드리스 브라우저(plan 위험 1(a))**
  - 노트북 여러 대(예: 4대 × 헤드리스 브라우저 50개)에서 학생 화면을 띄운다.
  - 교수가 넘긴 시각과 각 화면의 iframe이 위치를 그린 시각(`deck:moved`)의 차이를 모은다. 시계 차이는 같은 기계의 서버 왕복으로 보정한다.
  - 같은 서버에 붙어야 하므로 서버를 한 컴퓨터(또는 배포 서버)에 두고 다른 컴퓨터들이 그 주소로 붙는다.
  - 성공 기준: p95 1초 이내, 유실 0.
- **실제 묶음**: `--deck`으로 보통 크기 묶음(그림 10장 안팎)을 올려 첫 로딩을 다시 잰다. 대응을 정한 뒤에도 다시 잰다.
- **실기기(plan 위험 1(b), 배포 뒤)**: 001 notes 위험 4의 실기기 확인 목록에 002 항목 두 개를 더했다(11, 12번).
