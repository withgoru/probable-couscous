# T008 구현 노트: 학생 코드 출석 서버

> 스펙과 plan에 없는, 구현하면서 내가 세운 계획과 판단의 요지다. 스펙이 우선한다. 고칠 부분이 있으면 알려 달라.

## 스펙과 plan에서 읽은 것

- AC12: 지금 코드나 바로 앞 코드를 넣으면 출석이다.
- AC13: 틀리면 정해진 문구가 나오고, 1분에 5번 틀리면 남은 초 동안 막는다.
- AC14: 마감되면 "출석 시간이 끝났습니다. 교수님께 수기 출석을 요청하세요."가 나온다.
- AC16: 한 회차에 한 번만 출석한다. 다른 기기로 다시 넣으면 "이미 출석했습니다."가 나온다.
- AC27: 자기 출석만 한다. 명단에서 빠졌거나 로그인이 끊긴 학생은 출석할 수 없다.
- 오류 표: 한 번 누른 출석은 두 번 기록되지 않는다.
- plan 인터페이스:
  - `POST /class/{id}/sessions/{s}/attendance {code, client_key}`
  - 응답은 200 `{status, already}`, 422, 429 `{retry_after}`, 409다.
  - 출석하면 교수에게 `attendance.tally`, 그 학생에게만 `attendance.mine`이 간다.

## 내가 정한 것

1. **확인 순서**(쓰기 잠금 안에서):
   1. 같은 누름의 재전송(같은 `client_key`의 코드 출석이 있음)이면 처음 답 `{present, already: false}`를 준다. 마감 뒤에도 같다.
   2. 이미 출석이면(코드 출석이 있거나 마지막 기록이 출석·수기) `{status, already: true}`다.
   3. 출석 받는 중이 아니면 409 AC14 문구다.
   4. 제한기 `attempt`로 막힘 확인 → 코드 확인 → 틀림 세기를 한 번에 한다(T003).
      - 막혔거나 이번 틀림으로 막히면 429 `{detail: "잠시 뒤에 다시 입력해 주세요. (N초)", retry_after}`와 `Retry-After` 머리글이다.
      - 그냥 틀리면 422 AC13 문구다.
   5. 맞으면 `code` 기록을 넣고, 커밋한 뒤 알린다.
2. **이미 출석한 학생이 틀린 코드를 넣으면 틀림으로 세지 않고 `already`를 준다.** 출석한 학생은 코드를 떠볼 이유가 없고, 답으로 알 수 있는 것도 없다.
3. **교수가 코드 출석을 결석으로 바꾼 학생(AC21)이 다시 넣으면 `{status: "absent", already: true}`다.**
   - 회차마다 코드 출석은 한 번이라(DB 고유 색인) 다시 출석되지 않는다. 교수의 판단이 이긴다.
   - **T021 화면에 넘길 질문**: 이때 "이미 출석했습니다."는 맞지 않는다. 화면은 `already && status === "absent"`면 다른 안내를 보여야 한다. 예: "교수님이 결석으로 처리했습니다. 수기 출석을 요청하세요."
   - 스펙에 없는 문구라 T021에서 정한다.
4. **교수가 결석으로만 둔 학생(코드 출석 전)은 열려 있는 동안 코드로 출석할 수 있다.** 마지막 기록이 결석일 뿐 코드 출석이 없기 때문이다.
5. **명단 항목은 쓰기 잠금 안에서 다시 찾는다.**
   - `identity.roster_entry_of`는 지금 명단(`removed_at IS NULL`)의 항목만 돌려준다.
   - 권한 판단과 쓰기 사이에 명단에서 빠졌으면 출석을 남기지 않고 403이다.
   - 이것은 권한 판단(C8)을 라우트로 옮긴 것이 아니라, 기록할 대상을 정하는 데이터 확인이다. 권한은 `attendance.self`가 정한다.
6. **입장하지 않은 학생의 거절 문구를 출석에 맞게 바꿨다**(T002 노트): "이 강좌에 입장한 학생만 출석할 수 있습니다. 강좌 링크를 다시 열어 입장해 주세요." `authz`의 `attendance.self` 거절 사유 `not_member_attend`가 이 문구다.
7. **알림 대상을 하나 더했다.** `ws_class`에 `MEMBER_ONLY`를 두었다.
   - `membership_id`가 같은 학생 화면만 받고, 번호는 떼고 보낸다.
   - 출석 수(`tally`)는 교수 화면만 받는다. 프로젝터는 받지 않는다(카드에 수를 띄우지 않는다).
8. **`realtime.publish_class`의 앞 세 인자를 위치 전용으로 바꿨다.** 발행 필드 이름으로 `request`를 쓸 수 있게 하려는 것이다(`attendance.mine`의 요청 상태). 키워드로 넘기던 곳은 없다.
9. **동시성.**
   - 출석, 이미 출석, 틀린 코드 모두 쓰기 잠금을 잡는다. 그래야 두 기기가 동시에 보내도 하나는 `already`가 된다(고유 색인 오류 500이 아니라).
   - 잠금 순서는 늘 DB 쓰기 잠금 → 제한기 잠금이라 교착이 없다.
   - 잠금 안의 일은 색인 읽기 몇 번, HMAC 두 번, 삽입 한 번이다.
10. **테스트 도우미**: 학생을 여러 명 넣을 때 마지막 메일이 다른 학생의 것일 수 있다. 그래서 받는 사람으로 메일을 찾게 고쳤다.
    - 메일 발송이 초당 8통이라, 한꺼번에 출석하는 기능 테스트는 6명으로 했다. 200명 측정은 T028에서 한다.

## 확인한 것

- 새 테스트는 처음에 33개가 실패했다. 지금은 38개, 서버 1121개, constitution 35개, ruff check가 통과한다.
- 변형 검사(서브에이전트): 32개 중 27개를 잡았다.
  - 살아남은 5개 중 하나는 동작이 같은 변형이었다(교수 화면은 멤버십 번호가 없다).
  - 나머지 4개는 테스트를 더해 모두 잡았다: `Retry-After` 머리글, 64자 `client_key`, 쓰기 직전 명단 확인, 명단 항목과 멤버십 번호가 다른 경우.
  - 커밋 전 발행도 잡았다. 발행 순간 다른 연결에서 기록이 보이는지 확인한다.
- 리뷰(서브에이전트) 반영:
  - 명단 확인을 트랜잭션 안으로 옮기고, 빠진 항목은 대상에서 뺐다.
  - 위 3번은 T021로 넘겼다.
  - 409·422·200의 차이로 알 수 있는 것은 출석이 열려 있는지뿐이고, 그것은 교실에서 누구나 안다.

## 확인이 필요한 질문

- 위 3번: 교수가 결석으로 바꾼 학생이 코드를 다시 넣었을 때 학생 화면의 문구. T021을 시작할 때 정한다.
