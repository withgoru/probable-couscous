# T007 구현 노트: 교수·프로젝터용 코드 받기 서버

> 스펙과 plan에 없는, 구현하면서 내가 세운 계획과 판단의 요지다. 스펙이 우선한다. 고칠 부분이 있으면 알려 달라.

## 스펙과 plan에서 읽은 것

- AC3: 코드는 15초마다 바뀐다. 교수 수업 화면, 프로젝터, 같은 교수가 연 다른 화면은 같은 순간에 같은 코드를 보인다.
- plan '코드 전달':
  - 응답은 `GET …/attendance/code` → `{current: {code, ends_at}, next: {code, ends_at}, closes_at, server_now}`다.
  - 열려 있지 않으면 409다.
  - 학생에게는 코드가 가지 않는다.

## 내가 정한 것

1. **권한은 `guard_class(Action.ATTENDANCE_MANAGE, …)`다**(plan).
   - 소유 교수만 받는다. 프로젝터도 교수 본인의 로그인으로 여는 화면이라 같은 쿠키로 받는다.
   - 학생과 다른 교수는 403 AC26 문구, 로그인하지 않은 사람은 401이다.
   - 보관된 강좌에는 열린 출석이 없으니 409다.
2. **열림 판단은 T005와 같다**(닫지 않은 창 + 마감 시각 전). 시간이 지나 닫힌 창, 마감한 창, 수업을 끝낸 회차, 예정 회차는 모두 409다.
   - 문구: "지금은 출석을 받고 있지 않습니다."
   - 고치는 방법(다시 받기)은 화면이 상자에서 보인다(T017).
3. **다음 코드는 마감 뒤의 칸이어도 준다.**
   - 서버가 받는 칸은 지금 칸과 바로 앞 칸뿐이라, 다음 코드를 미리 알아도 이점이 없다.
   - 마감되면 창이 닫혀 받지 않는다. 연장하면 같은 난수라 그대로 맞는 코드가 된다.
   - 화면은 마감 시각에 코드를 숨긴다(T015).
4. **응답은 200·409 모두 `Cache-Control: no-store`다.** 브라우저나 중간 프록시가 지난 코드를 주지 않게 하려는 것이다.
5. **다른 강좌의 회차 번호는 404다.** 먼저 `load_session`으로 확인한다.

## 확인한 것

- 새 테스트는 처음에 7개가 실패했다. 지금은 12개, 서버 1082개, ruff check가 통과한다.
- 변형 검사(서브에이전트): 21개 중 20개를 잡았다.
  - 살아남은 하나(권한을 `session.present`로 바꾸기)는 보관된 강좌에서만 차이가 난다.
  - "보관된 강좌는 409 '지금은 출석을 받고 있지 않습니다.'" 테스트를 더해 잡았다.
- 리뷰(서브에이전트) 반영:
  - 수업을 끝낸 회차가 409인 테스트를 더했다(이 라우트는 회차 상태를 따로 보지 않고, 종료가 창을 닫는 것에 기댄다).
  - "학생 응답에 코드가 없다" 테스트를 넓혔다. 수업 상태, `attendance.updated` 발행, `events` 기록 어디에도 창의 난수가 없는지 본다.
  - 6자리 코드 값은 시각 문자열에 우연히 들어 있을 수 있어 값으로는 찾지 않는다.
