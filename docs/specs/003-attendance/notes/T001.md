# T001 구현 노트: 출석 스키마와 필수 회귀 넓히기(C6, C7)

> 스펙과 plan에 없는, 구현하면서 내가 세운 계획과 판단의 요지다. 스펙이 우선한다. 고칠 부분이 있으면 알려 달라.

## 스펙과 plan에서 읽은 것

- plan 데이터 모델: `classrooms.attendance_minutes`, `attendance_windows`(상태 표), `attendance_marks`·`attendance_requests`·`attendance_decisions`(추가만).
- 학생은 명단 항목 번호와(학생이 직접 한 일이면) 멤버십 번호로 가리킨다. 이메일·이름·학번 열이 없다(C7).
- 지우기는 보관 6개월 정리 때뿐이다(사용자 결정 2026-11-27).

## 내가 정한 것

1. **지우기는 트리거로 막지 않는다.** 정리 작업이 지울 수 있어야 하기 때문이다. 대신 소스 검사 테스트로 막는다.
   - 기록 표를 고치거나 지우거나 덮어쓰는 문장은 `purge.py` 밖에 둘 수 없다.
   - 표 이름을 변수로 넘기는 경우도 잡는다. 기록 표 이름과 `DELETE FROM`·`REPLACE`가 한 파일에 함께 있으면 거절한다.
2. **`INSERT OR REPLACE`를 트리거로 막는다.** 리뷰에서 나온 것이다.
   - REPLACE는 겹치는 행을 지우고 다시 넣어 UPDATE 트리거를 피한다. 실제로 승인을 거절로 바꿀 수 있었다.
   - 0001 `events_no_replace`와 같이, 고유 키가 겹치는 삽입을 먼저 막는 트리거를 세 기록 표에 두었다.
   - 막는 키는 번호, 코드 출석(회차·학생), 요청(회차·학생), 처리(요청 번호)다.
3. **`roster_entry_id`에는 외래 키를 두지 않는다.** 001의 C7 테스트가 명단을 가리키는 표를 `member_identities` 하나로 제한하기 때문이다. `events.subject_roster_entry_id`와 같은 방식이다.
4. **plan보다 DB에서 더 막은 것**(C13):
   - 기록 종류와 행위자가 맞아야 한다.
     - 코드 출석은 학생 본인만 한다. 이때 `actor_ref`가 그 멤버십이고, `client_key`는 1~64자다.
     - 그 밖의 기록은 교수가 하고, 멤버십과 `client_key`가 없다.
   - 승인 기록에는 요청 번호가 반드시 있다. 다른 기록에는 요청 번호가 없다.
   - 승인 기록은 요청과 같은 회차·학생을 가리키고, 요청 하나에 하나다.
   - 창 규칙:
     - 마감 시각은 연 시각보다 뒤여야 하고, 닫은 시각은 연 시각보다 앞일 수 없다.
     - 난수는 16진 32자다.
     - 연 방식은 `start`·`reopen` 둘뿐이다.
   - 모든 회차·멤버십·요청 참조는 `(id, classroom_id)`로 묶어 같은 강좌 것만 가리킨다(C5).
5. **C7 검사**: `test_schema.py`의 C5·C7 표 목록에 새 표 넷을 넣었다. 출석 표에는 `name`·`student`가 들어간 열이 아예 없는지 더 넓게 따로 본다(`student_name` 같은 열도 잡는다).
6. **기존 테스트 두 곳을 고쳤다.**
   - `test_schema.py`의 마이그레이션 목록에 0004를 더했다.
   - `test_session_schema.py`의 0002→최신 업그레이드 테스트는 이제 0003 다음에 0004도 적용된다. 그래서 "첫 번째가 0003"으로 바꿨다.

## T009에 넘길 것

- 사유 검사(`length(trim(reason))`, 원래 길이 200자 이하)에서 SQLite `trim()`은 공백만 지운다. 탭·줄바꿈·전각 공백은 지우지 않는다.
- 그래서 T009는 서버에서 앞뒤 공백을 지운 값을 검사하고, 지운 값을 저장해야 한다. 그러지 않으면 DB가 500을 낸다.

## 확인한 것

- 처음에 새 테스트 16개가 실패했다(표가 없었다). 지금은 서버 948개, constitution 35개, ruff check가 통과한다.
- 변형 검사(서브에이전트): 53개를 넣어 15개가 살아남았다. 의미 있는 생존은 테스트를 더해 다시 돌렸고, 남은 9개와 새 트리거·검사 4개를 모두 잡았다.
  - 생존 하나는 테스트 잘못이었다. 요청 테스트의 멤버십 닉네임이 겹쳐, 중복 요청이 엉뚱한 이유로 실패하고 있었다.
- 받아들인 생존:
  - `attendance_marks_latest` 색인: 성능용이다.
  - `attendance_marks_one_approval` 색인: 덮어쓰기 막기 트리거가 같은 경우를 먼저 막는다. 트리거를 지울 때를 대비해 둔다.
  - 문자열을 이어 붙여 만든 표 이름: 소스 검사의 한계다.
- 리뷰(서브에이전트) 결과: 중간 1건(REPLACE), 낮음 5건이 나왔다. 넷은 반영했고, 사유 저장은 T009로 넘겼다. T005~T012가 쓸 흐름(다시 받기, 재전송, 승인, 입장하지 않은 학생 바꾸기, 정리 순서)을 막는 제약은 없다는 확인을 받았다.
