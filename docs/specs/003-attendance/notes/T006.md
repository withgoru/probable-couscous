# T006 구현 노트: 연장·마감·다시 받기 서버

> 스펙과 plan에 없는, 구현하면서 내가 세운 계획과 판단의 요지다. 스펙이 우선한다. 고칠 부분이 있으면 알려 달라.

## 스펙과 plan에서 읽은 것

- AC4: **5분 연장**은 마감 시각을 5분 늦추고, **출석 마감**은 확인 대화상자를 거친 뒤 닫는다(대화상자는 화면 몫).
- AC5: 마감한 뒤 **출석 다시 받기**는 정해 둔 시간만큼 새 코드로 다시 연다. 이미 출석한 학생은 그대로다.
- AC7: 이어서 하기 뒤에는 교수가 다시 받기로 연다.
- plan 인터페이스:
  - 진행 중이 아니면 409 "진행 중인 수업에서만 출석을 받을 수 있습니다."다.
  - 연장·마감할 창이 없으면 409다.
  - 권한은 `session.present`다.
  - 행동마다 `events`에 기록하고, `version`을 올려 `attendance.updated`를 발행한다.

## 내가 정한 것

1. **세 라우트가 한 흐름(`_control`)을 쓴다.**
   - 쓰기 트랜잭션을 열고, 그 안에서 시각을 읽는다. 잠금을 기다린 요청이 지난 시각으로 쓰지 않게 하려는 것이다.
   - 회차가 진행 중인지 보고 → 창을 바꾸고 기록하고 → `version`을 1 올리고 → 커밋한 뒤 `attendance.updated{session_id, window, version}`를 발행한다.
   - 거절(409)하면 아무것도 쓰지 않고 발행하지 않는다.
2. **권한은 `guard_class(Action.SESSION_PRESENT, …)`다.** 다른 교수와 학생 모두 403 AC26 문구를 받는다. 보관된 강좌는 409 "보관된 강좌는 수업을 시작할 수 없습니다."다.
   - 수업 중에는 보관할 수 없어서(002 AC46) 실제로는 거의 나오지 않는 경우다.
   - DB를 직접 바꿔 진행 중 회차가 남은 보관 강좌를 만든 테스트로, 권한 판단이 먼저 막는 것을 확인했다.
3. **연장은 지금이 아니라 마감 시각에서 5분을 더한다.** 누를 때마다 5분이고, 두 번 누르면 10분이다. 화면(T017)은 요청 중에 버튼을 흐리게 한다.
4. **연장·마감은 열린 창이 있어야 한다.**
   - 시간이 지나 닫혔으면(화면이 아직 모를 수 있다) 409다.
   - 문구는 무엇이 잘못됐고 어떻게 하는지 말한다: "출석 시간이 이미 끝났습니다. 다시 받으려면 '출석 다시 받기'를 눌러 주세요."
   - 마감을 눌렀는데 이미 끝나 있었다면, 화면은 이 409를 받고 `live`를 다시 받아 닫힌 상태를 보이면 된다(T017).
5. **다시 받기는 열려 있으면 409다.** 문구: "이미 출석을 받고 있습니다. 마감한 뒤 다시 받아 주세요."
   - 시간이 지나 닫힌 창이 남아 있으면, 마감 시각으로 닫고(마감 기록 없음) 새 창을 연다(새 난수 = 새 코드).
   - 출석 기록은 건드리지 않는다.
6. **응답은 `{window, version, server_now}`다.** 연장 뒤에 화면이 남은 시간을 다시 맞추라고 `server_now`를 넣었다. 새 창의 코드는 T007의 코드 받기에서 가져온다.
7. **기록 내용**:
   - 연장: `{session_id, window_id, closes_at}`
   - 마감: `{session_id, window_id, by: "professor"}`
   - 다시 받기: 마감(필요할 때) 뒤에 `attendance_opened{…, minutes}`
   - 개인정보는 넣지 않는다.

## T016·T019·T020에 넘길 것

- 지금 클라이언트(`classLive.ts`의 `apply`)는 `attendance.updated`를 `version`을 올리는 발행으로 알아보지 못한다.
- 그래서 연장·마감·다시 받기 뒤 다음 `position`이 오면 `version`이 하나 건너뛴 것으로 보고, 모든 화면이 `live`를 다시 받는다. 깨지지는 않지만 200명이 한꺼번에 다시 받는다.
- 화면 작업에서 `attendance.updated`를 `apply`에 더해 `attendance.window`와 `version`을 바로 적용해야 한다.

## 확인한 것

- 새 테스트는 처음에 23개가 실패했다. 지금은 30개, 서버 1070개, constitution 35개, ruff check가 통과한다.
- 변형 검사(서브에이전트): 25개 중 22개를 잡았다. 살아남은 셋은 테스트를 더해 모두 잡았다.
  - 트랜잭션 안에서 발행하기: 발행하는 순간 다른 연결로 읽은 `version`·창이 발행한 값과 같은지 본다.
  - `attendance.manage`로 권한 판단하기: 보관 강좌의 409 문구를 고정했다.
  - 강좌 전체의 최대 `version` 읽기: 다른 회차의 `version`이 더 큰 경우를 넣었다.
- 리뷰(서브에이전트):
  - 동시 요청은 쓰기 잠금으로 하나씩 처리된다. 연장 둘은 둘 다 되고, 다시 받기 둘은 두 번째가 409다.
  - `attendance.updated`에는 코드·난수·출석 수가 없어 학생에게 가도 된다.
  - 위 "넘길 것"이 나왔다.
