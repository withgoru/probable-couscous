# T005 구현 노트: 수업 시작에 출석 열기, 이어서 하기·종료와의 관계, `live`의 출석 상태

> 스펙과 plan에 없는, 구현하면서 내가 세운 계획과 판단의 요지다. 스펙이 우선한다. 고칠 부분이 있으면 알려 달라.

## 스펙과 plan에서 읽은 것

- AC2: 수업을 시작하면 출석이 바로 열린다.
- AC7: 이어서 하기로 다시 열면 출석은 저절로 열리지 않는다.
- plan 데이터 모델: 수업 종료는 같은 트랜잭션에서 열린 창의 `closed_at`을 채운다.
- plan 인터페이스:
  - `live`에 `attendance`를 더한다. 교수는 창, `present`, `roster`, `pending`, `server_now`를, 학생은 창, 자기 `status`, 자기 요청, `server_now`를 받는다.
  - `attendance.updated`는 열기·연장·마감·다시 받기·수업 종료 때 `version`과 함께 발행한다.

## 내가 정한 것

1. **시작·종료는 002의 `session.updated`만 발행한다. plan·tasks와 다른 점이다.**
   - plan·tasks에는 시작·종료 때도 `attendance.updated`를 보낸다고 적혀 있다.
   - 클라이언트(`classLive.ts`)는 `session.updated`를 받으면 역할과 `version`에 관계없이 `live`를 통째로 다시 받는다. 그 안에 출석 창이 있으니 따로 보낼 필요가 없다.
   - 같은 `version`으로 두 번 보내면 하나는 버려진다. `version`을 두 번 올리면 002의 발행 순서 테스트와 뜻이 바뀐다.
   - `attendance.updated`는 회차 상태가 그대로인 변화(연장·마감·다시 받기, T006)에만 쓴다.
   - **T016·T019·T020에 넘길 것**: 화면은 `attendance.updated`만 기다리지 말고, `live`를 다시 받을 때마다 `attendance.window`에서 상태를 정해야 한다. 그래야 시작·종료 때 학생의 출석코드 단계(AC11)와 프로젝터 카드(AC8)가 바뀐다.
2. **출석 열기는 수업 시작과 같은 트랜잭션이다.**
   - 수업 시작 → 진행 중 확인(`_went_live`, 보관 중 강좌 막기) → 창 넣기 → `attendance_opened` 기록 → `session_started` 기록 순서다.
   - 기록이 실패하면 수업도 출석도 열리지 않는다(테스트).
3. **종료 때 이미 시간이 지나 닫힌 창은 마감 시각을 `closed_at`으로 쓰고, `attendance_closed`는 기록하지 않는다.** 실제로 열려 있던 창을 닫을 때만 `{by: "session_end"}`로 기록한다.
4. **`_change`의 `apply(row, now)`는 이제 `datetime`을 받는다.** 출석 함수가 시각 계산을 하기 때문이다. 쓰는 곳 세 군데는 모두 `.isoformat()`으로 바꿨다.
5. **출석 DB 함수는 `app/attendance_state.py`에 모았다.** 열기, 닫기, 창 요약, 마지막 기록, 교수용 수, 학생 본인 상태가 들어 있다.
   - 멤버십 → 명단 항목 찾기는 `identity.roster_entry_of`에 두었다. `member_identities`는 identity 모듈만 건드린다(C9 테스트).
   - 학생 본인 상태는 그 학생의 마지막 기록 한 줄만 읽는다. 수업 화면을 다시 받을 때마다 학생 수만큼 불리기 때문이다.
6. **`live`의 창 요약**: `{open, opened_at, closes_at, closed_at}`이다. 시간이 지나 닫힌 창은 `closed_at`이 마감 시각이다. 한 번도 열지 않은 회차(예정)는 `window: null`이다.
7. **기존 테스트 두 곳을 고쳤다.**
   - `test_class_state.py`: `live`의 키 목록에 `attendance`를 더했다.
   - `test_restart_class.py`: 재시작 전후 비교에서 `server_now`만 뺐다. 창은 그대로 같아야 한다.

## 확인한 것

- 새 테스트는 처음에 13개가 실패했다. 지금은 19개, 서버 1040개, constitution 35개, ruff check가 통과한다.
- 변형 검사(서브에이전트): 27개 중 17개를 잡았다(하나는 전체 테스트에서).
  - 살아남은 10개는 모두 출석 기록, 요청, 창 여럿이 있어야 드러나는 곳이었다. 그런 기록을 만드는 라우트는 T006~T010에서 생긴다.
  - 그래서 DB에 직접 넣는 테스트 다섯 개를 더했다. 마지막 기록, 학생끼리 섞이지 않음, 대기 요청 수, 요청 상태, 최신 창, 다른 회차의 창을 본다.
  - 다시 돌려 9개를 잡았다. 남은 하나(창 요약의 `classroom_id` 조건)는 회차 번호가 전역이라 드러나지 않는 C5 이중 확인이다.
- 리뷰(서브에이전트):
  - 위 1번이 plan과 다르다는 지적을 받았다. 동작에는 해가 없음을 확인했다.
  - 마지막 기록 하위 질의에 `classroom_id` 조건을 더했다(C5).
  - 학생 상태 질의를 한 줄 읽기로 바꿨다.

## 확인이 필요한 질문

- 위 1번(시작·종료는 `session.updated`만)이 plan의 `attendance.updated` 목록과 다르다. 그대로 두려면 다음에 plan을 고칠 때 "시작·종료는 `session.updated`로 알리고 화면은 `live`에서 창을 읽는다"로 옮기면 된다.
