# T003 구현 노트: 코드 계산, 받는 칸, 틀린 코드 제한기, 상태 계산

> 스펙과 plan에 없는, 구현하면서 내가 세운 계획과 판단의 요지다. 스펙이 우선한다. 고칠 부분이 있으면 알려 달라.

## 스펙과 plan에서 읽은 것

- plan 기술 선택:
  - 코드는 `HMAC-SHA256(SERVER_SECRET, "attendance:{창}:{난수}:{칸}")`에서 만든 6자리다.
  - 칸 = `floor(유닉스 ms / 15000)`.
  - 받는 칸은 지금 칸과 바로 앞 칸이다.
  - 틀린 코드 제한기는 메모리의 미끄럼 창이다. 1분에 5번 틀리면 가장 오래된 틀림 + 60초까지 막는다.
  - 상태는 마지막 기록으로 정한다.
- plan 확장 지점: 상태의 종류는 계산 함수 하나(`attendance_status`)에만 둔다.

## 내가 정한 것

1. **모듈 `app/attendance_core.py` 하나에 네 가지를 둔다.**
   - DB와 시계는 모르고, 시각은 부르는 쪽이 넘긴다.
   - 001의 `challenges.compute_code`와 같은 방식으로 HMAC 앞 8바이트 % 100만을 쓴다.
   - 비밀값이 비어 있으면 같은 문구로 거절한다.
2. **칸 번호는 `datetime` 차이를 15초로 정수 나누기 해서 구한다.** 부동소수 없이 정확하고, 시간대가 없는 시각은 거절한다.
3. **입력 형식은 ASCII 숫자 6자리만 받는다.**
   - `isdigit()`는 전각 숫자도 참이라 정규식으로 본다.
   - 이 검사는 빠른 길이 아니라 꼭 필요하다. `hmac.compare_digest`는 ASCII가 아닌 문자열에 오류를 내서, 없으면 500이 된다.
4. **두 칸 모두 비교한다.** 어느 칸에서 맞았는지가 응답 시간으로 드러나지 않게 하려는 것이다.
5. **제한기에 `attempt(키, 시각, 확인 함수)`를 더했다**(리뷰에서 나온 것).
   - "막혔는지 보기 → 코드 확인 → 틀리면 세기"를 한 잠금 안에서 한다.
   - 따로 부르면 한 학생이 동시에 여러 요청을 보내 5번 제한을 넘길 수 있다.
   - T008은 이것을 쓴다. 확인 함수는 DB를 쓰지 않는 코드 비교라 잠금을 오래 잡지 않는다.
6. **잠금이 풀린 직후의 동작.** 1분 안의 틀림을 세는 미끄럼 창이라, 풀린 직후 한 번 더 틀리면 약 1초 다시 막힐 수 있다(앞의 네 번이 아직 1분 안이면).
   - AC13 "1분 안에 5번 틀리면"의 문자 그대로의 동작이라 그대로 둔다.
   - 화면은 매번 서버가 준 남은 초를 보인다.
7. **상태 값은 `present`/`manual`/`absent`로 고정한 문자열이다.** 기록은 번호 순으로 넘겨야 하고, 기록이 없으면 결석이다(T010의 질의에서 `ORDER BY id`).

## 확인한 것

- 새 테스트는 처음에 모듈이 없어 수집 단계에서 실패했다. 지금은 단위 테스트 40개, 서버 995개, ruff check가 통과한다.
- 변형 검사(서브에이전트): 47개 중 12개가 살아남았다.
  - 6개는 동작이 같은 변형이었다: `==` 비교, `match`, `max(0, …)`, 잠금 없애기(GIL), 정수 칸 계산 두 가지.
  - 나머지 6개는 테스트를 더해 모두 잡았다: 계산식 고정값, 앞자리 0만 나오는지, 정확히 60초 된 기록, 최근 다섯 번 기준, 각 함수의 오래된 기록 지우기.
  - 새 `attempt`의 잠금 확인 빼기, 오래된 기록 지우기 빼기도 잡았다.
- 리뷰(서브에이전트): 동시 요청으로 제한을 넘는 문제를 고쳤다(5번). T007은 지금 함수로 지금·다음 코드와 경계 시각을 만들 수 있다.
  - 화면에 보인 코드는 처음 보인 뒤 최대 30초 동안 받는다(바로 앞 칸까지 받으므로).
